## 2. 发现并修复的 Bug（3 个，均有真实数据佐证）

### BUG-1 check 环节预算超限，流水线 500 中断
- 现象：stage5 接受后 stage6 崩溃 `check 预算超限: 估算 12259 > 上限 12000`
- 根因：`config.yaml` check=12000 按旧短篇配置，5000 字档章节 + 对照资料必然超
- 修复：check 12000→20000，editorial 16000→24000（预防同性质超限）

### BUG-2 节点崩溃后管线卡死，无法续跑
- 现象：修复原因后 confirm 返回假视图 `done=true`，管线永远停在"有断点（next=stage6）、无确认点"状态
- 根因：`confirm` 端点遇"无 interrupt"直接返回视图，不处理崩溃遗留的待执行节点
- 修复：无 interrupt 且 `st.next` 非空时 `graph.invoke(None)` 从 checkpoint 恢复；同时给 start/confirm 补 `cost.set_project`（见 BUG-3）

### BUG-3 成本记账全量丢失（静默）
- 现象：真实消耗数十万 token，`cost.json` 恒为 0
- 根因：LangChain `response_metadata` 的键是 `token_usage`，代码取 `.get("usage")` 恒 None → `record_usage` 静默返回；且 confirm/start 线程未标记项目（threading.local）
- 修复：新增 `cost.extract_usage()`（兼容 token_usage/usage/usage_metadata 三种键位），替换 factory + chat 三处调用；start/confirm 调 `set_project`
- 验证：修复后首次调用即入账（6519 tokens / $0.0012）

## 4. 遗留与洞察

1. **第 1 章带 9 条已接受的审查意见**（作者裁量放行）：多为设定细节与正文措辞的偏差（王秀兰养母/护士身份、怀表刻字等）。清单在 stage6 报告中，可在 UI 里逐条复核。
2. **系统性洞察：设定文档自身可能自相矛盾**（世界观"顾宛如" vs 人物档案"顾婉如"）。修复循环无法收敛的原因往往是"正典本身分裂"。改进方向：stage1-3 产出后增加设定间一致性预检（或规划师预检），成本远低于逐章修复。
3. **迭代修复的发散风险**：修复指令若不知道全部正典，可能引入新偏差（实测出现）。改进方向：fix_action 生成时附上相关档案原文，让作者按证据决策。
4. 章节实际字数（5370/5959/8335）与 5000 字目标符合；第 3 章 8335 字略超，写作档 max_tokens=8192 未截断。

## 4-C 成本优化（OPT-A/B/C/D）实施与实测

本报告 §2~§4 的测试完成后，实施四项成本优化（详见 docs/成本优化需求分析.md）：

- **OPT-A 分级窗口**：`memory.full_window=1`——最近 1 章全文 + 其余章/卷摘要（原为 4 章全文）
- **OPT-B 抽取三合一**：`agents/understanding.py::understand_chapter` 一次调用产出 摘要+状态卡+关系（原 3 次独立调用），stage7 与 `_finalize_chapter` 均已接入，失败自动退回独立路径
- **OPT-C 抽取纯文本化**：`chapter_plaintext` 统一喂正文，去除 scenes JSON 开销
- **OPT-D 写作 prompt 重排**：memory 块前置、packet 后置，摘要在前全文在后（缓存前缀友好）

**实测对比**：OPT 前基线 173 万 tokens @9 章；OPT 后增量 92.1 万 tokens @11 章（第 10~20 章）——**平均 8.4 万 token/章，较此前约 11 万+/章下降 ~27%**；调用数 197 次/20 章 ≈ 10 次/章。缓存命中率的最终变化需在 DeepSeek 控制台下一批次账单观察（预期 >75%）。
> 修正（同日）：经服务端日志核对，OPT 批次实为**第 14~20 章（7 章）**，第 10~13 章属暂停前批次——per-chapter 归因以本节前文时间线为准，"4 倍降幅"表述作废，保守结论为 **30% 左右**。
