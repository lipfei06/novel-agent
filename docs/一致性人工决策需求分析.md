# 一致性审查人工决策闭环 需求分析与接口设计

> 版本：v1.0 ｜ 日期：2026-09-21 ｜ 状态：已实现（commit 65dc5d1）
> 范围：stage6 一致性检查的确认载荷（`graph/graph.py`）、审查报告前端渲染（`web/src/components/StageView.jsx`）、确认交互（`web/src/components/ConfirmView.jsx`）

---

## 1. 背景

stage6 审查员发现写手错误后已有"auto-fix ≤3 次 → 超限转人工"链路，但"转人工"环节存在四个缺口：

1. **超限无视觉警示**：后端打了 `needs_human` 标记，前端渲染分支未使用，作者只能从"还有 N 个问题"间接猜；
2. **AI 建议未展示**：问题的 `fix_action`（AI 给出的修复思路）后端有、前端丢，作者看不到矛盾的处理建议；
3. **人工无修复通道**：确认卡只有 接受/重新生成/编辑JSON 三个动作，"编辑"分支后端预留的 `apply_edits` 定点修复协议无 UI 入口；
4. **修复后报告过期**：`apply_edits` 应用后直接 break，作者看到的仍是修复前的旧报告。

## 2. 目标与非目标

**目标**：修复超限时，作者能看到（a）醒目警示与处理指引、（b）每条矛盾的描述/位置/AI 建议、（c）按矛盾下达定点修复指令并在修复后看到复查结果。最终决策权（修复/重查/放行）始终在作者。

**非目标**：修改 auto-fix 策略本身；审查员提示词调整；快捷章节路径（不走 stage6）的审查补充。

## 3. 需求详述

### FR-1 超限警示横幅

| 项 | 内容 |
|---|---|
| 触发 | `needs_human == true`，或（存在未解决问题 且 `auto_fix_attempts >= 3`） |
| 内容 | 琥珀色横幅：超限说明 + 三种处理方式指引（填指令修复 / 重新生成 / 接受放行） |

### FR-2 矛盾卡片增强

每条未解决问题展示：`description`（矛盾描述）、`kind`（中文化：设定冲突/人物OOC/时间线/文风/逻辑）、`location`（位置）、`fix_action`（AI 建议，有则显示"AI 建议：…"）。已解决与未解决问题分区展示，已修复数量与修复次数随文显示。

### FR-3 指令式人工修复

| 项 | 内容 |
|---|---|
| 输入 | 每条未解决问题提供：场景下拉（选项来自确认载荷的 `scenes`，id+标题）+ 修复指令文本框 |
| 为什么下拉 | 问题的 `location` 是展示文本，`locate_scene` 只按 `scene.id` 精确匹配——直接传 location 会定位失败，必须由作者从场景清单选 id |
| 提交 | 组装 `fixes: [{scene_id, instruction}]`，至少一条非空指令才可提交 |

### FR-4 修复后复查

`apply_edits` 应用全部指令后**不退出确认循环**，重新执行一致性检查并再次弹确认卡——作者看到的是修复后的真实报告，循环由作者决定何时结束。

## 4. 接口设计

### 4.1 stage6 确认载荷（后端 → 前端）

```json
{
  "issues": [{"severity": "high", "kind": "setting", "location": "场景三",
              "description": "眼睛颜色与第3章矛盾", "fix_action": "改为灰色", "resolved": false}],
  "needs_human": true,
  "auto_fix_attempts": 3,
  "scenes": [{"id": "sc_1", "heading": "开场"}]
}
```

变更点：新增 `scenes` 字段（`[{id, heading}]`，随载荷实时生成）。其余字段不变。

### 4.2 决策协议（前端 → 后端，`confirm` 接口 body）

| 动作 | body | 后端行为 |
|---|---|---|
| 放行 | `{"action": "accept"}` | 章节+报告入 state，进 stage7 |
| 重查 | `{"action": "regenerate"}` | 回循环头，重新检查当前章节 |
| **指令修复** | `{"action": "edit", "data": {"apply_edits": true, "fixes": [{"scene_id": "sc_2", "instruction": "眼睛改回灰色"}]}}` | 逐条 `edit_scene` 定点改写 → **重新检查** → 再次弹确认卡（本次变更点：原实现 break，现 continue） |

### 4.3 组件职责

- `StageView`：新增可选 props `onSubmit` / `busy`；stage6 分支替换为有状态组件 `Stage6View`（警示横幅 + 矛盾卡片 + 修复输入区 + 提交按钮）。其他 stage 渲染不受影响（props 可选，缺省无行为变化）。
- `ConfirmView`：向 `StageView` 透传 `onSubmit` / `busy`。

## 5. 验收标准

1. auto-fix 未超限：展示与旧版一致（通过/问题列表），无横幅、无输入区——零回归；
2. 超限：横幅出现，每条矛盾可（选场景 + 填指令）提交，按钮在无有效指令时禁用；
3. 提交修复后：重新检查，若问题解决则显示"✓ 通过（含人工修复记录）"，未解决则继续留在确认卡；
4. 159 个既有测试全绿（mock 确认流不受影响）；前端 `vite build` 通过。

## 6. 已知边界

- 一次指令修复针对单场景定点改写，跨场景联动矛盾需多条 fix 或回 stage5 重写；
- `needs_human` 的判定阈值固定引用 `max_auto_fix` 配置（默认 3），前端横幅文案中的"3 次"由 `auto_fix_attempts` 实际值渲染，两者天然一致。
