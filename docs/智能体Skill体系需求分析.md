# 智能体 Skill 体系需求分析

> 版本 v1.0 ｜ 状态：待评审 ｜ 改造对象：全部生成/审查类智能体的知识注入方式
> 关联：对话式创作智能体需求分析（章节助手 agent 化）、规划智能体 ReAct 改造（ask_author 模式）、成本优化需求分析（token 预算）

---

## 1. 背景与问题

### 1.1 现状：手艺知识散落三层，且不可运营

系统现有 12 个智能体（6 生成 + 3 审查/抽取 + 3 辅助），每个的"怎么做好"知识散在三处：

| 层 | 位置 | 内容 | 问题 |
|---|---|---|---|
| 阶段提示词 | `agents/*.py` 的 `SYSTEM_PROMPT` | 角色定义 + 输出格式 + 少量手艺规则（如 packet 的防剧透规则） | **改一次要动代码**；手艺内容与角色定义混在一起，越写越长 |
| 题材档案 | `src/novel_agent/profiles/*.yaml` | style_preset（pov/tone/pace/钩子频率）+ world_requirements + red_lines | 这是"这本书是谁"（题材身份），不是"这类东西怎么做"（手艺）；两者已混 |
| 素材库 | `library/presets.py`（技法/原型/模板） | 34 条技法（guidance/checklist/examples 结构化）、性格原型、人物模板 | 是**数据**，由检索注入；但没有"什么时候该用哪个手法"的上层编排 |

已实证的痛点：
- **手艺上限取决于提示词**：结构化阶段（立项/世界观/人物/总纲）都是单次 structured 输出，质量完全由注入的指导决定，当前指导普遍只有 2-4 句
- **经验无法沉淀**：跑书过程中验证过的经验（如 ch23 实测"梗要长在人物性格里，精准投放 1-2 个"）只能留在对话记录里，下次生成不会受益
- **问作者只覆盖一处**：stage4r 有 clarify_with_author（≤2 问带选项），立项/人物等阶段同样存在方向分叉（结局基调、感情线数量），却没有澄清机制——生成完再返工成本更高

### 1.2 行业参照（2026-09 调研）

- Agent Skills（SKILL.md）自 2025-10 Anthropic 发布、2025-12 开放标准化（agentskills.io），2026 年已是主流做法：Cursor/Codex 等均支持，"写一次、跨 agent 复用"
- 核心机制**三级渐进披露**：启动只载 name+description（~100 token/个）→ 命中任务载正文 → 附件按需载
- 定位共识：MCP 管"连工具/数据"，SKILL 管"程序性知识（怎么做）"。本项目要引入的正是后者

### 1.3 结论：需要，但形态是"整合"而非"新增"

在三层之上再加第四层必然打架（同一件事四处理念不一致，模型听谁的）。正确做法：**新建一个统一的 skill 层收纳手艺知识，同步把 SYSTEM_PROMPT 瘦身**，题材档案与素材库保留并在 skill 中被引用。

## 2. 目标与非目标

**目标**
1. 新建 `skills/` 文件目录 + `SkillLoader`：每个智能体阶段注入一个对应 skill 正文（markdown，含 frontmatter 元数据）
2. skill 支持**声明式 ask_author 检查点**：作者输入存在方向分叉时，生成前先问（复用现有 interrupt/确认通道），把"生成后返工"前移为"生成前澄清"
3. SYSTEM_PROMPT 瘦身：只留角色定义 + 输出格式；手艺规则迁入 skill（先迁 packet 防剧透规则）
4. 全部 skill 为仓库内 markdown 文件，非开发者可维护；token 开销有界（每阶段一次调用最多 +1 个 skill 正文，约 300-600 token）

**非目标**
- 不引入 SKILL.md 的可执行脚本能力（我们只需要知识注入，不需要 agent 执行 skill 附带代码）
- 不对接 agentskills.io 生态的 skill 分发（格式对齐其 frontmatter 惯例即可，自管自用）
- 不改变确认流/图结构：skill 是提示词层的改造，不新增图节点
- 不动题材档案与素材库的数据结构

## 3. 总体设计

### 3.1 Skill 文件格式

```
skills/
  concept.md        # 选题策划 skill（stage0）
  world.md          # 世界观构建 skill（stage1）
  character.md      # 人物设计 skill（stage2）
  outline.md        # 总纲架构 skill（stage3）
  volume.md         # 分卷规划 skill（stage3b）
  packet.md         # 章节规划 skill（stage4b）
  write.md          # 写手 skill（stage5）
  consistency.md    # 一致性审查 skill（stage6 check）
  editorial.md      # 总编审读 skill（stage6 editorial）
  understanding.md  # 记忆抽取 skill（stage7）
```

每个文件 = frontmatter（YAML）+ 正文（markdown 手艺指导）：

```markdown
---
name: write-craft
description: 单章正文写作手艺：开场钩子、展示vs讲述、对白潜台词、梗的精准投放、结尾钩子模板
apply_stage: stage5            # 对应哪个智能体阶段，一个 skill 只服务一个阶段
priority: 50                   # 与题材档案/技法库冲突时的排序（数值大者后注入=更具体）
ask_author:                    # 声明式问作者检查点（可为空）
  - when: "立意未指明结局基调"
    question: "结局希望是爽文收尾，还是留白/遗憾？"
    options: ["爽文收尾", "留白/遗憾", "悲剧收尾"]
    default: "爽文收尾"
---

（正文：给模型看的手艺指导，用要点+正反例，300~600 token）
```

### 3.2 加载与注入（渐进披露）

```
SkillLoader（启动时只解析全部 frontmatter，常驻内存 ≈ 10×100 token）
    │
    ├─ describe()  → 供诊断/前端展示"本阶段搭载了什么 skill"
    └─ load(stage) → 返回命中 skill 的正文文本（一次一个，无检索匹配成本）
```

注入点：`build_messages(...)` 增加 `skill_text` 参数，拼在 system prompt 之后：

```
{SYSTEM_PROMPT（瘦身后）}

<skill name="write-craft">
{skill 正文}
</skill>

{style_directive（题材档案，不变）}
{stage_guidance（技法库检索结果，不变）}
```

注入优先级（冲突时后者覆盖前者语义）：SYSTEM_PROMPT < skill 正文 < 技法库 guidance < 题材档案 style_directive。理由：越靠后越"具体于本书"。

### 3.3 ask_author 检查点

复用 stage4r 已验证的交互模式，推广为通用三步：

1. **声明**：skill frontmatter 列出 `ask_author` 检查点（when/question/options/default）
2. **判定**：该阶段生成前，用 cheap 档跑一次轻量判定（输入 = 当前用户输入 + 检查点列表，输出 = 需要问的 ≤2 问；mock 模式返回空）。判定失败/超时 → 跳过澄清直接生成（与 stage4r 同款降级）
3. **交互**：命中则 interrupt，payload `{"type": "ask_author", "questions": [...]}`，走现有确认通道；前端问题卡（选项按钮 + 默认项）复用 stage4r 已规划的问题卡设计（注意：该问题卡前端尚未实现，见 §7 依赖）

成本：每章/每阶段多一次 cheap 调用（约 500 token），仅当该阶段 skill 声明了检查点。

### 3.4 与现有层的关系（收敛表）

| 现有内容 | 处置 |
|---|---|
| `SYSTEM_PROMPT` 里的手艺段落（如 packet 防剧透规则、write 的场景块说明） | 迁入对应 skill 正文；SYSTEM_PROMPT 只留角色+格式 |
| `profiles/*.yaml` style_preset | 保留（题材身份层）；skill 正文中引用其取值（如"show_vs_tell 见档案值"） |
| `TECHNIQUE_PRESETS` 技法库 | 保留（数据层）；skill 写"编排逻辑"（何时用哪类手法），不复制具体手法内容 |
| 章数硬绑定、长度约束、标题约束 | 保留在代码——这些是校验逻辑不是手艺知识 |

## 4. 每个 Agent 的 Skill 清单与设计

> 正文大纲给出该 skill 必须覆盖的知识点；实施时每条展开为要点+正反例。标 ★ 的是从已实测经验沉淀（有本项目跑书证据）。

### 4.1 concept.md — 选题策划（stage0）

- **一句话立意三要素** ★：主角 + 核心冲突 + 代价/风险；检验标准"去掉任何成分故事就塌"（DeepSeek 实测自述的高质量表述，沉淀为规则）
- 卖点差异化：一句话说清"同类书很多，这本凭什么"；避免与题材头部作品同质
- 期待感设计：立项书要埋"读者为什么点进来"的承诺（悬念/爽点/情感许诺）
- 篇幅-体量匹配：10 万字撑不起三条主线，目标字数反推主线数量
- **ask_author**：结局基调（爽文/留白/悲剧）；主角性别与年龄段（未指明时）；敏感红线确认（题材 red_lines 之外的作者私货）

### 4.2 world.md — 世界观构建（stage1）

- **冰山原则**：写给读者的露出 20%，库内备足 80%；设定条目分"露出层/支撑层"
- **冲突承载力检查**：每个设定必须能回答"它能产生什么戏"；产生不了戏的设定是装饰
- 力量体系三件套：来源、代价、限制（无代价的力量毁掉张力）
- 命名一致性：术语表驱动（glossary 先行，地名/组织名/术语统一词根）
- **ask_author**：写实度档位（纯现实/轻设定/高概念）；是否需要力量体系

### 4.3 character.md — 人物设计（stage2）

- **欲望 vs 需要**：主角表层想要的 vs 内心真正缺的，弧光=两者关系的变化
- **缺陷驱动**：缺陷必须能制造剧情（固执→错失/误会），不选"与剧情无关的缺陷"
- 配角功能论：镜像（照出主角另一种可能）/反衬/工具人最小化——每个配角给一个存在理由
- 声线区分法 ★：每人一段"语气采样"（句长/口头禅/回避什么话题），写手照采样写对白（真假千金 20 章验证：voice 字段具体的角色，后续章对白一致性显著更好）
- 关系网张力：两人关系至少含一种"不对等"（信息差/权力差/情感差）
- **ask_author**：感情线数量（无/单线/多线）；反派类型偏好（人性反派/环境与制度/无明确反派）

### 4.4 outline.md — 总纲架构（stage3）

- 结构比例：起承转合在卷间的分配参考（如 10 万字 2 卷：卷一占 55%，卷末必有大转折）
- **中点反转**：全书 50% 处安排"读者以为的 A 其实是 B"级翻转
- 卷末钩子递进：每卷结尾钩子强度必须高于上一卷（可量化：信息量/危险等级/情感烈度）
- 伏笔账本平衡：埋点数与回收点数配平，跨卷伏笔标注预计回收卷
- 时间线预算：全书跨度明确（如"不超过一年"），防止后期"十年过去了"
- **ask_author**：结构偏好（传统三幕/单元剧拼盘/双线并进）；关键转折密度（密/疏）

### 4.5 volume.md — 分卷规划（stage3b）

- 卷内高潮排布：每卷至少一个小高潮（卷 30%~40% 处）+ 卷末大钩子
- 卷间递进不重复：上一卷用过的冲突类型（身份危机/信任危机/外部威胁）下一卷必须换型或升级
- 章数契约重申：chapter_count 由配置硬绑定，规划只填剧情
- **ask_author**：卷结构形态（连环案单元型 / 一卷一大事连续型）

### 4.6 packet.md — 章节规划（stage4b）

- **场景目标唯一论**：一场一目标，写不出目标的场景删掉或合并
- 节拍情绪曲线：一章 3~5 拍，张弛交替；连续两拍同强度 = 节奏事故
- **伏笔种子三要素**：可隐藏（不点破）、可回收（有明确回收场景）、有成本（埋了要占篇幅）
- **reference_seeds 规范** ★：只写可直接检索的短实体词（人名/地名/物件名），禁写叙事风格长句（ReAct 改造 P1 的根治知识面）
- **防剧透纪律**（从 packet.py SYSTEM_PROMPT 迁入）：只看当前卷规划，不泄露后文真相；foreshadow 只填本章埋的种子
- **梗的精准投放** ★：优先长在人物性格里的梗 > 情境梗 > 网络热梗；每章 1~2 个封顶，投放在情绪转折点当"透气阀"，绝不放进高潮场景（ch22 丢梗 / ch23 落梗的对照实验结论）
- **ask_author**：复用 clarify_with_author 的方向分叉判定（本 skill 不新增声明，已有机制）

### 4.7 write.md — 写手（stage5）

- **展示 vs讲述操作法**：情绪用动作/生理反应/环境折射展示；信息用讲述；比例参照档案 show_vs_tell
- **开场钩子三板斧**：in medias res（动作中开场）/ 反常细节 / 对白切入；首段禁超 150 字设定说明
- 对白潜台词：人物说的 ≠ 人物想的；关键对话至少一层潜台词
- 场景过渡：时间/空间跳变用锚点物（同一物件/天气/声音）衔接
- **结尾钩子模板库**：信息钩（新线索）/ 危机钩（险境降临）/ 情感钩（关系突变）/ 悬念钩（反常沉默），按本章类型选一
- 字数纪律：目标字数 ±25% 由 tune_length 兜底，写手按 ±10% 控制（代码约束保留，skill 只写意识）

### 4.8 consistency.md — 一致性审查（stage6 check）

- 冲突分级：硬冲突（事实矛盾：道具/时间线/人物状态，必须修）> 软矛盾（性格漂移，建议修）> 风格漂移（提示即可）
- **误报抑制**：时间线模糊表述（"过了几天"）不算冲突；角色未登场不算漏洞——只报"与已确立事实矛盾"的
- 修复指令写法：必须引用原文位置 + 给出可执行的改法，禁止"建议加强一致性"式空话

### 4.9 editorial.md — 总编审读（stage6 editorial）

- 节奏诊断：连续 N 章无钩子升级 = 节奏疲软；连续两章同类型高潮 = 重复
- 伏笔回收率审计：对照伏笔账本，回收率 < 60% 且临近完结时警示
- 人物弧光完整度：主要角色在结尾必须能看到 start→end 的状态变化
- 全局视角纪律：总编可见全书（含结局），审查"是否兑现立项承诺"，与规划侧的防剧透相区分

### 4.10 understanding.md — 记忆抽取（stage7）

- 事件粒度标准：一章 2~5 条事件；"可被后文引用的事实"才入账本（内心活动不入）
- 道具登记触发：满足任一才登记——跨章复用 / 承载秘密 / 被多人争夺；一次性消耗品不登记 ★（真假千金"怀表未登记"教训：关键道具漏登记导致后文查证空转）
- 状态变化判定：只记录"变化量"（受伤/获利/关系变化），不复述未变项
- 抽取纪律：宁缺毋滥——错误的事实比缺失更毒（污染后续所有章的正典注入）

## 5. 实施计划

| 阶段 | 内容 | 工作量 |
|---|---|---|
| P1 骨架 | `skills/` 目录 + 10 个 skill 文件（正文按 §4 大纲展开）+ SkillLoader + build_messages 注入 + packet 防剧透迁移 + 单测（加载/注入/缺文件降级） | ~1.5 天 |
| P2 问作者 | ask_author 判定器（cheap 档，含 mock 空返回与降级）+ interrupt 接线 + 前端通用问题卡（复用 stage4r 设计）+ concept/character 两阶段试点 | ~1 天 |
| P3 补全评估 | 审查/抽取侧 3 个 skill 上线；跑一章对照（同章开/关 skill 各生成一次）评估质量差异；真实验证 token 增量符合预期 | ~1 天 |

每阶段独立可交付、可回滚（skill 注入失败 = 空串，生成照常）。

## 6. 测试与验收

- 单测：SkillLoader 加载/缺文件/格式错误降级；build_messages 注入位置与优先级；ask_author 判定 mock 返回空
- 管线测试：mock 模式全流程跑通（skill 注入不破坏既有 163 项测试）
- 真实验收：① 新项目设定阶段触发至少一次 ask_author 问题卡并正常续跑；② 同章开/关 skill 对照生成，人工盲评；③ 成本流水确认单章 token 增量 < 2%

## 7. 依赖与风险

| 风险/依赖 | 缓解 |
|---|---|
| 前端 ask_author 问题卡尚未实现（stage4r 遗留） | P2 一并实现，两处共用 |
| skill 与题材档案/技法库语义冲突 | 注入优先级固定（§3.2）+ priority 字段预留；验收时对照检查 |
| skill 正文膨胀（写嗨了塞满 2000 token） | 验收红线：单 skill 正文 ≤ 600 token，CI 可加长度检查 |
| prompt 注入面扩大（skill 文件即提示词） | skill 仅仓库内文件、无网络来源；文档中声明"skill 内容视为可信配置" |
| 结构化输出被长指导带偏（模型在正文里聊天） | invoke_structured 既有 JSON 重试兜底；skill 明确"本 skill 只影响内容，不影响输出格式" |
